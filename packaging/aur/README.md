# Cross Cleaner — AUR

Файлы для публикации Cross Cleaner в Arch User Repository. Это отдельные
git-репозитории на AUR, в основной репозиторий проекта они попадать не должны.

Пакетов два: `cross-cleaner` (сборка из исходников) и `cross-cleaner-bin`
(готовые бинарники из релиза). Оба живут здесь и публикуются одним воркфлоу.

## Состав

| Файл | Назначение |
|---|---|
| `PKGBUILD` | Пакет `cross-cleaner`: компилирует тег на машине пользователя |
| `bin/PKGBUILD` | Пакет `cross-cleaner-bin`: ставит бинарники из релиза |
| `LICENSE` | 0BSD — лицензия на файлы пакета (требование Arch), общая для обоих |
| `.gitignore` | Исключает артефакты `makepkg`, общий для обоих |
| `README.md` | Этот файл (для людей, а не для AUR) |
| `.SRCINFO` | Снимок метаданных для веб-интерфейса AUR — см. ниже |

Итоговые `PKGBUILD` и `.SRCINFO` в AUR генерируются из этого каталога воркфлоу
`.github/workflows/aur.yml` — см. ниже. `.SRCINFO` в этом каталоге ничего не
публикует: AUR получает тот, который печатает настоящий `makepkg` в контейнере,
а лежащий рядом файл — просто снимок ручной сборки и может отставать.

## Два пакета

|  | `cross-cleaner` | `cross-cleaner-bin` |
|---|---|---|
| Откуда бинарники | `cargo build --release` на машине пользователя | ассеты `-no-updater` из релиза на GitHub |
| Источники | архив тега | архив тега (только метаданные) + 6 ассетов |
| Время «сборки» | ~час, ~640 крейтов | секунды |
| Нужен `rust`/`cargo` | да | нет |
| Нужен доступ к crates.io | да | нет |
| `makedepends` | `icoutils`, `desktop-file-utils`, `appstream`, `alsa-lib`, `mesa`, `wayland` | `icoutils` |
| Что установится | `cross-cleaner`, `cross-cleaner-tui`, `cross-cleaner-cli`, desktop-файлы, иконка 96×96, appdata | то же самое |

Набор файлов у пакетов одинаковый, включая третий бинарник `cross-cleaner-cli`.
Разница только в том, кто компилирует код, и поэтому оба PKGBUILD содержат
`provides=('cross-cleaner')` и `conflicts=('cross-cleaner')`: вместе они не
ставятся, второй заменяет первый вместо конфликта файлов.

`-bin` берёт именно набор `-no-updater`: он собран с `--no-default-features`, то
есть без пути самообновления, и не будет воевать с pacman за собственные файлы.
Обычные ассеты (`Linux-Cross_Cleaner_GUI` и т. д.) для этого пакета не годятся,
и `prepare()` в `bin/PKGBUILD` специально проверяет, что в скачанном не осталось
кода `selfupdate`.

## Публикация: воркфлоу

Публикация автоматическая. Открываете **Actions → Update AUR packages → Run
workflow** и заполняете форму:

| Вход | Что это | Когда менять |
|---|---|---|
| `version` | версия, то есть имя тега без `v` (например `2.0.4.2.5`) | всегда: это версия релиза |
| `pkgrel` | значение `pkgrel` в PKGBUILD, по умолчанию `1` | если исправляется сам пакет, а не приложение: та же версия, следующий `pkgrel` |
| `target` | `both`, `cross-cleaner` или `cross-cleaner-bin` | когда меняется только один пакет |
| `dry_run` | прогнать всё и показать diff, но не пушить | на первом запуске — всегда |

С обычными значениями (`pkgrel=1`, `target=both`) версия уезжает в оба пакета
сразу: они привязаны к одному тегу.

**Исправление пакета без нового релиза.** Если ошибка в самом PKGBUILD, а версия
уже опубликована, выпускается та же `version` с поднятым `pkgrel` и только тот
пакет, который правился: `version=2.0.4.4`, `pkgrel=2`,
`target=cross-cleaner-bin`. Так вышло с первой публикацией `-bin`: makepkg кладёт
исходники в `$srcdir` симлинками, а `file(1)` без `-L` симлинки не
разыменовывает, поэтому проверка архитектуры отвергала исправные файлы у всех,
кто собирал пакет. Ровно поэтому `target` — отдельный вход: поднимать `pkgrel`
пакету, в котором ничего не менялось, незачем.

Значения внутри маркеров `AUR-VERSION` в этом репозитории — не то, что сейчас на
AUR: публикация переписывает их в клоне AUR-репозитория, а здесь остаётся то,
что оставила последняя правка шаблона.

![workflow](https://github.com/Cross-Cleaner/Cross-Cleaner/actions/workflows/aur.yml/badge.svg)

Общая часть (`.github/actions/aur-prepare`), одинаковая для обоих пакетов:

1. проверяет, что введённая строка — корректная версия для pacman;
2. проверяет, что тег `v<версия>` существует в репозитории;
3. скачивает архив тега и считает sha256;
4. проверяет, что архив распаковывается в каталог, который ожидает `PKGBUILD`
   (иначе об этом узнаёшь только через 40 минут компиляции);
5. настраивает SSH к AUR, сверяя ключ сервера с отпечатком с главной страницы
   AUR, а не доверяя `ssh-keyscan` на слово;
6. клонирует репозиторий AUR.

Дальше job `update-aur` (`cross-cleaner`) копирует `PKGBUILD`, `LICENSE`,
`.gitignore` и переписывает значения между маркерами `AUR-VERSION` — версию,
`pkgrel` и checksum архива. Job `update-aur-bin` (`cross-cleaner-bin`)
дополнительно:

7. качает шесть ассетов `-no-updater` — GUI, TUI и CLI для `x86_64` и для
   `aarch64`, потому что в PKGBUILD нужен checksum каждой архитектуры, которую
   он объявляет в `arch=`, а сборочный раннер — только одна из них;
8. проверяет, что скачанное — это ELF нужной архитектуры и что в нём нет
   `selfupdate` (тот же канарейка-тест, что релизный пайплайн применяет к `.deb`);
9. считает sha256 всех семи файлов и переписывает блок между маркерами: версию,
   `pkgrel`, два массива источников (по архитектуре) и два массива checksum-ов.

Затем оба job-а общим шагом (`.github/actions/aur-publish`) печатают `.SRCINFO`
настоящим `makepkg` в контейнере `archlinux:latest`, проверяют, что версия в нём
сдвинулась и что ни один checksum не остался `SKIP`, показывают diff и коммитят
в `master`.

### Что нужно настроить один раз

Секрет репозитория `AUR_SSH_PRIVATE_KEY` — приватная часть ключа, который
зарегистрирован в аккаунте AUR (см. «Ручная публикация» ниже, шаг с
`ssh-keygen`): **Settings → Secrets and variables → Actions → New repository
secret**.

Публичный ключ при этом уже должен быть в профиле AUR: **My Account → Add SSH
Key**.

Больше ничего: **репозиторий в AUR создаётся первым push-ом**. Отдельного
«создать пакет» в AUR нет — если клонировать ещё не существующий `pkgbase`,
сервер отдаёт пустой репозиторий (git предупреждает `You appear to have cloned
an empty repository`), а сам пакет появляется при первом push. Оба job-а это
учитывают: на пустом клоне ветка `master` создаётся, а не переключается, и
проверка «нечего пушить» смотрит на untracked-файлы, иначе первая публикация
завершилась бы успешно, ничего не создав.

Важное следствие: AUR отдаёт **не** пустой репозиторий, если пакет с таким
именем когда-то удаляли. Тогда push упрётся в non-fast-forward (см. ниже) — это
лечится `git pull --rebase origin master` перед push.

Порядок относительно релиза: job `cross-cleaner-bin` не может работать, пока
релиз на GitHub лежит **драфтом** — ассеты драфта недоступны анонимной загрузке,
и шаг скачивания упадёт на 404 (что правильно: `curl --fail` не позволит
записать страницу ошибки вместо бинарника). Job `cross-cleaner` к статусу релиза
безразличен: ему нужен только тег.

### Галочка dry run

Вход `dry_run` прогоняет все проверки, показывает diff и останавливается перед
`git push` — в тех job-ах, которые выбрал `target`. Стоит начинать с него: он
бесплатно ловит ошибку в версии, опечатку в `pkgrel` и неопубликованный релиз до
того, как что-то уедет в AUR.

`pkgrel` проверяется до клонирования AUR-репозитория: значение, которое pacman не
примет, обрывает job на первом шаге, а не на последнем.

## Ручная публикация

Если воркфлоу недоступен — например, до настройки секрета — пакет можно
залить руками. Кнопки «Submit Package» на aur.archlinux.org **нет**: AUR
перешёл на git по SSH.

### 1. Аккаунт и SSH-ключ

Зарегистрируйтесь на https://aur.archlinux.org/passwd/. Создайте отдельный
ключ — основной GitHub-ключ переиспользовать не стоит:

```bash
ssh-keygen -f ~/.ssh/aur
```

Публичный ключ (`~/.ssh/aur.pub`) вставьте в профиль AUR. В `~/.ssh/config`:

```
Host aur.archlinux.org
  IdentityFile ~/.ssh/aur
  User aur
```

### 2. Клонировать и запушить

Для `cross-cleaner`:

```bash
repo=/home/roman/Documents/GitHub/Cross-Cleaner
git clone ssh://aur@aur.archlinux.org/cross-cleaner.git /tmp/aur-cross-cleaner
cd /tmp/aur-cross-cleaner
cp "$repo/packaging/aur/"{PKGBUILD,LICENSE,.gitignore} .

# проставить версию, pkgrel и checksum в блок между маркерами, затем:
makepkg --printsrcinfo -p PKGBUILD > .SRCINFO
git add PKGBUILD .SRCINFO LICENSE .gitignore
git commit -m "cross-cleaner <версия>"
git push
```

Для `cross-cleaner-bin` то же самое, но источник — `packaging/aur/bin/PKGBUILD`,
а checksum-ов семь, и в блоке их два массива:

```bash
repo=/home/roman/Documents/GitHub/Cross-Cleaner
git clone ssh://aur@aur.archlinux.org/cross-cleaner-bin.git /tmp/aur-cross-cleaner-bin
cd /tmp/aur-cross-cleaner-bin
cp "$repo/packaging/aur/"{LICENSE,.gitignore} .
cp "$repo/packaging/aur/bin/PKGBUILD" PKGBUILD

url=https://github.com/Cross-Cleaner/Cross-Cleaner
v=2.0.4.2.5   # та же версия, что в pkgver
curl -sSfLO "$url/archive/refs/tags/v$v.tar.gz"
for arch in Linux Linux-Arm64; do
  for c in GUI TUI CLI; do
    curl -sSfLO "$url/releases/download/v$v/${arch}-Cross_Cleaner_${c}-no-updater"
  done
done
sha256sum v$v.tar.gz Linux-* Linux-Arm64-*   # что куда — по порядку в блоках PKGBUILD

makepkg --printsrcinfo -p PKGBUILD > .SRCINFO
git add PKGBUILD .SRCINFO LICENSE .gitignore
git commit -m "cross-cleaner-bin <версия>"
git push
```

`updpkgsums` здесь не помощник: ему доступны только источники текущей
архитектуры, поэтому массив второй архитектуры всё равно придётся считать
вручную, скачав `Arm64`-ассеты. Воркфлоу делает это сам.

**Требования AUR, которые ломают пуш:**

- Пуш только в ветку `master`. Если ветка называется иначе — `git branch -M master`.
- **AUR отклоняет non-fast-forward.** Локальная история не должна расходиться с
  удалённой: если расходилась, `--force` не поможет, серверный хук его отклонит.
  Сначала `git pull --rebase origin master`, потом push. Это же ждёт при первом
  push-е имени, пакет с которым когда-то удалили: репозиторий там не пустой.
- `PKGBUILD` и `.SRCINFO` должны быть в одном коммите. Забыли `.SRCINFO` —
  `git commit --amend --add .SRCINFO`, а не новый коммит.
- `LICENSE` обязателен: пакеты без лицензии не промотируются в официальные
  репозитории.
- Имя и email коммитов берутся из глобального git-конфига, и после пуша их
  сменить почти невозможно. Для другого авторства задайте их локально до
  коммита: `git config user.name "..." && git config user.email "..."`.

## Требования для сборки

### `cross-cleaner`

**`base-devel` должен быть установлен.** `rust` и `cargo` входят в
`base-devel`, и AUR-хелперы их **не ставят автоматически** — сборка падает с
`cargo: command not found`. Это давнее соглашение AUR: пакеты предполагают
наличие base-devel в среде сборки.

```bash
sudo pacman -S --needed base-devel
```

Остальные зависимости (`icoutils`, `desktop-file-utils`, `appstream`,
`alsa-lib`, `mesa`, `wayland`) хелпер подтянет сам — они указаны в `makedepends`,
в отличие от `rust`.

**Нужен доступ к crates.io.** Cargo скачивает ~640 крейтов с `index.crates.io` /
`static.crates.io` плюс git-зависимость `gpu-allocator` с GitHub. В сетях, где
crates.io недоступен, сборка падает с
`SSL connect error (Recv failure: Connection reset by peer)` — это не ошибка
пакета. Обходится VPN либо зеркалом реестра в `~/.cargo/config.toml`.

### `cross-cleaner-bin`

Из `base-devel` нужен он сам (в частности `fakeroot`, `file`, `binutils` для
`strings`), из дополнительных — только `icoutils`, чтобы достать иконку из
`.ico` в архиве тега. Компиляции нет, поэтому нет ни `rust`, ни обращений к
crates.io.

Сеть нужна к `github.com`: архив тега отдаёт `codeload.github.com`, ассеты —
редирект на `objects.githubusercontent.com`. Это как раз тот случай, когда
`cross-cleaner-bin` собирается там, где `cross-cleaner` не может:
единственная внешняя зависимость — сам GitHub, и занимает это секунды.

## Проверка перед отправкой

```bash
bash -n PKGBUILD                      # синтаксис
makepkg --printsrcinfo -p PKGBUILD   # метаданные
makepkg -s --noconfirm               # сборка (у -bin это только скачивание)
makepkg --packagelist                # какие файлы попадут в пакет
```

Для `-bin` полезно посмотреть содержимое пакета и убедиться, что скачанный
бинарник не тянет за собой самообновление:

```bash
pkg=$(makepkg --packagelist)
bsdtar -tf "$pkg"                     # три бинарника, desktop-файлы, иконка, appdata
bsdtar -xOf "$pkg" usr/bin/cross-cleaner > /tmp/cc
strings /tmp/cc | grep -i selfupdate  # не должна печатать ничего
```

Полная сборка `cross-cleaner` долгая: ~640 крейтов плюс `lto = true`,
`codegen-units = 1`, `opt-level = "z"` из workspace-профиля. Это настройка
upstream, а не этого PKGBUILD. `cross-cleaner-bin` собирается за время загрузки
семи файлов.

## Особенности пакета

**Версия привязана к тегу, а не к ветке.** Источник обоих пакетов — архив тега
(`.../archive/refs/tags/v${pkgver}.tar.gz`), а не `git+`. VCS-источник всегда
идёт за default-веткой, и каждый пользователь собрал бы то, что в `main`
лежало на момент сборки, а не тот релиз, который опубликован. С архивом
версия ниже называет ровно один коммит. Побочный эффект: имена без суффикса
`-git` корректны по правилам AUR. У `cross-cleaner-bin` к архиву добавлены
шесть ассетов, и тоже с привязкой к тегу — `releases/download/v${pkgver}/...`.

**Функции `pkgver()` нет ни в одном из пакетов.** Раньше она считала версию
через `git describe`, и это делало пакет непригодным: значение всегда
расходилось с тем, что показано в веб-интерфейсе AUR.

**Три бинарника.** `cross-cleaner` (оконное приложение), `cross-cleaner-tui`
(терминальное) и `cross-cleaner-cli` (для скриптов). `cargo` называет их по
именам пакетов (`desktop`, `tui`, `cli`), в обоих PKGBUILD они
переименовываются, чтобы `Exec=` в desktop-файлах не зависел от конкретного
релиза. В `-bin` это ещё и обязательно: ассеты называются
`Linux-Cross_Cleaner_GUI-no-updater`, и такие имена в `/usr/bin` не годятся.

**`--no-default-features` везде.** Путь самообновления выключен намеренно:
версией установленного пакета управляет пакетный менеджер. В `cross-cleaner`
это флаг сборки, в `cross-cleaner-bin` — выбор ассетов `-no-updater`, который
`prepare()` ещё и проверяет. Так же поступает `.deb`-сборка — см.
`packaging/linux/nfpm.yaml`.

**Зависимости.** Список `depends` перенесён из `nfpm.yaml`, где он тоже
поддерживается вручную: winit через `x11-dl` открывает весь X11-стек через
`dlopen`, поэтому эти библиотеки не видны ни в `ldd`, ни в проверках
зависимостей, но без них окно не откроется. В `-bin` список тот же: у
prebuilt-бинарника те же `dlopen`-вызовы, а проверить их автоматически нечем.

**Иконка.** `crates/winicon/assets/icon.ico` содержит один кадр 96×96, и
`icotool` извлекает его как есть. В отличие от AppImage-сборки, здесь ничего не
растягивается под 128 и 256 — установлен единственный настоящий размер. Чтобы
добавить остальные, нужен мастер-PNG ≥512px в `crates/winicon/assets`. В
`-bin` иконка приезжает из архива тега по той же причине: релиз публикует
только бинарники, отдельного PNG в ассетах нет.

`icotool` при этом печатает два предупреждения — `x_pels_per_meter field in
bitmap should be zero` и то же для `y_pels_per_meter`. Это свойство самого
апстримного `.ico`: в BITMAPINFOHEADER этих полей быть не должно, а тот, кто
собирал файл, их проставил. Для пакета это не ошибка — кадр извлекается,
`icotool` завершается успешно, и сборка идёт дальше. Если бы он всё-таки ничего
не извлёк, сборка упала бы на следующей проверке — `icotool extracted no frame
from icon.ico`.

**Две лицензии.** `LICENSE` в этом каталоге (0BSD) — лицензия на файлы пакета,
требование Arch для допуска в официальные репозитории. Лицензия самой программы
(GPL-3.0-or-later) указана в поле `license=` обоих PKGBUILD и в `LICENSE`
основного репозитория проекта.

**`prepare()` идемпотентна.** Иконка извлекается во временный каталог, а не
прямо в `$srcdir`: makepkg переиспользует существующий `$srcdir`, если изменился
только PKGBUILD, и старая схема падала с `mv: ... are the same file`. В `-bin`
на это же рассчитаны проверки скачанных файлов: они не пишут в `$srcdir`.

### Только `cross-cleaner`

**`--locked` не используется.** `Cargo.lock` в релизных тегах устарел
относительно манифестов в тех же тегах: в `v2.0.4.2.5` крейты объявляют
`version = "2.0.4"`, а lock-файл помнит `2.0.1`, поэтому cargo требует
перезаписи lock и `--locked` обрывает сборку до компиляции. То, ради чего
`--locked` добавлялся, всё равно держится: lock уже фиксирует ревизию
`gpu-allocator` из `Cargo.toml`'s `[patch.crates-io]`, и cargo не пересматривает
записи, которые удовлетворяют манифестам. Релизные воркфлоу самого проекта
`--locked` тоже не передают.

**Снимаются флаги компилятора makepkg.** `build()` делает `unset CFLAGS
CXXFLAGS CPPFLAGS FCFLAGS FFLAGS ARFLAGS LDFLAGS LTOFLAGS RUSTFLAGS`. Arch
экспортирует `CFLAGS` в окружение сборки, их подхватывает крейт `cc` и
передаёт компилятору, которым `ring`'s build.rs собирает крипто-ядро, после
чего финальная линковка теряет `-l` для этого архива и падает на всех символах
ring:

```
ld.lld: error: undefined symbol: ring_core_0_17_14__x25519_sc_mask
```

Сама ring при этом собрана верно: build-скрипт выдаёт и `rustc-link-lib`, и
`rustc-link-search`, а в архиве лежат все 157 символов. Проверено отсечением на
уменьшенном крейте (`ureq → rustls → ring`): без `CFLAGS` собирается, с ними —
нет, а LTO, `RUSTFLAGS`, `LDFLAGS` и остальное окружение makepkg ни при чём.

### Только `cross-cleaner-bin`

**Версия внутри бинарника — трёхкомпонентная.** `prepare()` в `PKGBUILD`
переписывает версию в исходниках, и бинарники печатают `2.0.4.2.5`. В
prebuilt-бинарнике править нечего: он собран `build_linux_no_updater` из того
же коммита, где версия в `Cargo.toml` — `2.0.4`, поэтому
`cross-cleaner --version` скажет `2.0.4` для пакета `2.0.4.2.5`. Четвёртый
компонент в cargo-версии не представим вообще, так что сократить эту разницу
нечем: она унаследована от того, как релизный воркфлоу версионирует сборку.
Метаданные при этом говорят полную версию — `pkgver`, иконка и appdata
проставляются из `$pkgver`.

**Checksum-ы на две архитектуры.** В блоке между маркерами два массива
источников и два массива checksum-ов. Архив тега попадает в оба (и его
checksum поэтому одинаковый), ассеты — разные: у `aarch64` в имени ассета есть
`Arm64`. `makepkg` выбирает массив по текущей машине, и `$CARCH` же выбирает
префикс имени файла в `prepare()`/`package()` — через одну функцию
`_asset_prefix()`, чтобы проверка и установка не разошлись.

**Архив тега нужен только ради метаданных.** Desktop-файлы, appdata и
`icon.ico` есть только в дереве. Компиляции из архива нет, поэтому
`desktop-file-utils` и `appstream` в `makedepends` не нужны: файлы не
создаются здесь, а релизный пайплайн проверяет ровно их теми же инструментами
перед загрузкой — см. `.github/actions/linux-package/action.yml`.

**Проверки скачанного.** `prepare()` отвергает сборку, если скачанный файл не
ELF нужной архитектуры (иначе на x86_64 спокойно встанет aarch64-бинарник,
который не запустится) и если в нём нашлась строка `selfupdate` (иначе
установится самообновляющаяся сборка, которая перезапишет себя в обход pacman).
Обе ошибки иначе всплыли бы только у пользователя.

## Известная проблема upstream

В релизных тегах `Cargo.lock` не соответствует манифестам: версии крейтов в
`Cargo.toml` подняты до `2.0.4`, а lock-файл остался на `2.0.1`. Пока это так,
`cargo build --locked` не работает ни на одном теге. Лечится регенерацией
lock-файла в релизном воркфлоу — например, добавлением
`cargo update --workspace` в задачу `formating_code` перед коммитом.

`cross-cleaner-bin` этой проблемой не задет: он ничего не собирает, а
`cross-cleaner` обходит её отказом от `--locked` (см. выше).
