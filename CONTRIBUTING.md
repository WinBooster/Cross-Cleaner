# 🤝 Contributing to Cross Cleaner

Thanks for taking the time to contribute! This file covers how to build, what a
good pull request looks like here, and — the part that is easy to get wrong —
**how to write commits so they show up in the release notes**.

For build, packaging and cross-compilation details see [BUILD.md](BUILD.md).

## 🚀 Before you start

```bash
git clone https://github.com/WinBooster/Cross-Cleaner.git
cd Cross-Cleaner
cargo build          # debug build
cargo test           # run the test suite
```

Rust 1.70 or higher is required. CI (`.github/workflows/dev_build.yml`) runs on
every pull request and push that touches Rust, Cargo, JSON or workflow files.

## ✅ Before you open a pull request

```bash
cargo fmt            # the CI job "Auto format code" reformats for you, do it locally
cargo test
cargo build          # make sure the workspace still compiles
```

## 🌿 Branches and pull requests

- Branch off `main`, one topic per pull request.
- Keep the PR title user-facing and specific. **The PR title is the text that
  appears in the release notes** — the individual commits inside a merged PR do
  not appear separately.
  - Good: `feat: native arm64 builds for Linux and Windows`
  - Bad: `fixes`, `update`, `wip`
- Describe what changed and how to verify it. Mention platform-specific effects:
  this project builds for Windows, Linux, macOS and Android, and a change that
  only makes sense on one of them should say so.

## 📝 Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/): a type, an
optional scope, then a short description in the imperative mood.

```
<type>(<optional scope>): <description>
```

### Types and where they end up in the release notes

GitHub generates the release notes automatically
(`generate_release_notes: true` in `.github/workflows/release.yml`) and sorts
entries into categories by keyword. With the repository defaults, these types
map as follows:

| Type | Release note category | Example |
| --- | --- | --- |
| `feat` | New Features | `feat: add arm64 installer for Windows` |
| `fix` | Bug Fixes | `fix(tui): fix encoding of non-ASCII program names` |
| `docs` | Documentation | `docs: document --no-default-features in BUILD.md` |
| `perf` | Other Changes | `perf: parallelize directory scanning` |
| `refactor` | Other Changes | `refactor: move path matching into database crate` |
| `build` / `ci` / `chore` / `test` | Other Changes | `build: use Inno Setup 7` |

Anything else lands in **Other Changes**, which is fine for maintenance commits —
but `refactor` and `perf` are worth splitting into a separate category in the
repository settings if they grow over time.

If you prefer not to use type prefixes, the equivalent emoji keywords work:

| Keyword | Category |
| --- | --- |
| `feat`, `:sparkles:`, ✨ | New Features |
| `fix`, `:bug:`, 🐛 | Bug Fixes |
| `enhance`, `:rocket:`, 🚀 | Enhancements |
| `docs`, `:memo:`, 📝 | Documentation |
| `BREAKING CHANGE`, `:warning:`, ⚠️ | Breaking Changes |

### Rules that decide whether your commit reaches users

1. **Never rewrite `main` history between releases.** A `rebase` or a force push
   after the previous tag drops commits out of the `previous tag → new tag`
   range, and those commits then never appear in the notes.
2. **Do not use `BREAKING CHANGE` casually.** It creates its own section at the
   top of the release page, so reserve it for changes that really do break
   existing setups, and explain the migration in the commit body or the PR.
3. **Describe the effect, not the diff.** `fix: fix crash when scanning a
   network share` is useful; `fix: fix` is not.

## 📦 Generated files — do not edit by hand

A few files are produced by CI and will be overwritten:

| File | Generated by |
| --- | --- |
| `LIST_WINDOWS.md`, `LIST_REGISTRY.md`, `LIST_LINUX.md`, `LIST_MACOS.md`, `LIST_ANDROID.md`, `LIST_CUSTOM.md` | `.github/workflows/update_program_lists.yml` |
| `version =` lines in `Cargo.toml` / `Cargo.lock` | the `formating_code` and release workflows |
| Sorting of `crates/database/*_database.json` | the `sort_json` job (sorted by `program`, case-insensitive) |

Edit the sources instead:

- program catalogs: `crates/database/*_database.json`
- built-in custom cleanings: `crates/cleaner/src/custom_cleaners.rs`
- `LIST_CUSTOM.md` and the "Built-in custom cleanings" sections are parsed out
  of `custom_cleaners.rs` by a regex, so keep the `id` / `program` /
  `category` / `path` field formatting in that file intact.
- links for the catalog tables: `crates/database/program_links.json`

The bot commits (`Auto format code`, `Auto-sorted JSON files by program field`,
`Auto-updated program catalogs`) are excluded from the release notes by author.

## 🚢 Release process (maintainers)

1. Run the **Release** workflow with the new version. It builds every platform
   and creates the release as a **draft** with auto-generated notes.
2. Review the assets and the notes on the draft, edit if needed, then publish it
   on the releases page.
3. Run the **Publish Release** workflow with the same version to submit the
   installer to winget and regenerate the `LIST_*.md` catalogs.

`secrets.WINGET_TOKEN` must be available in the repository for step 3.
